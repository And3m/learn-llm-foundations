Advanced prompting gives a request more information or more compute at inference time. The useful patterns do one of these things:

- Show the structure of a problem.
- Generate alternatives.
- Check a draft.
- Connect the model to evidence and skills that are not in its parameters.

<Callout title="Learning objectives">
  <ul>
    <li>Know when explicit reasoning and decomposition can help.</li>
    <li>Design refinement loops and ensemble loops with evaluators that you can check.</li>
    <li>Connect retrieval and tools. Do not use their outputs as trusted instructions.</li>
  </ul>
</Callout>

<h2 id="chain-of-thought">Chain-of-thought prompting</h2>

Chain-of-thought prompting asks the model to write intermediate reasoning before its conclusion. A few-shot prompt can show the desired reasoning pattern. A zero-shot prompt can ask for a careful solution. This often helps tasks that have many dependent operations. The reason is that the model gets more tokens to represent the calculation.

The method also has costs:

- Longer outputs increase latency.
- The output can show internal text that is not related to the task.
- The output can give a convincing explanation for a wrong result.

Thus, use reasoning text as a candidate derivation, not as proof. High-risk answers still need checks that you can run, source evidence or an independent verifier.

<Callout title="Reasoning text is not proof">
  <p>Fluency measures how probable an explanation sounds. Verification measures if its claims and operations are correct. Keep these two judgments separate.</p>
</Callout>

<h2 id="problem-decomposition">Problem decomposition</h2>

Decomposition divides a difficult request into smaller subproblems. There are three usual designs:

- **Sequential:** The output of one step becomes the input to the next step.
- **Parallel:** The model solves independent subtasks separately. Then the results are combined.
- **Least-to-most:** The model starts with simpler prerequisites and builds the final answer step by step.

<DecompositionDiagram />

Good subproblems have explicit inputs, limited outputs and a method to find failures. Thus, you can observe the workflow and try a failed step again. Bad decomposition only spreads the original ambiguity across more model calls. It can also move an early error forward. Thus, keep the source evidence and validate intermediate results at the main boundaries.

Use this design test: could you give each step to a different worker and check it independently? If you could not, the division can be only a show. It does not decrease the complexity.

<h2 id="self-refinement">Self-refinement</h2>

Self-refinement uses a loop, for example **draft, critique, revise**:

1. The model writes a draft.
2. The critique names defects against explicit criteria.
3. The revision corrects these defects and keeps the correct material.

When you put the roles into different prompts or model calls, the state changes can be clearer.

Refinement works best when you can see the quality problem locally. Examples are missing requirements, claims without support, invalid code and inconsistent formatting. It is less reliable when the model cannot find its own wrong idea. Thus:

- Limit the number of iterations.
- Keep the best candidate that passed verification.
- Stop when the measured improvement stops.

<h2 id="ensembling">Ensembling</h2>

Ensembling samples many candidate responses and combines them. It can use a majority vote, a vote with confidence weights, ranking or a separate judge. Self-consistency applies this idea to reasoning paths. It generates different solutions and selects the answer that most paths agree on.

The benefit depends on diversity and on the quality of the evaluator:

- Five samples that are almost the same give little independent evidence.
- Majority agreement can make a shared bias stronger.
- A model judge can prefer good language to correct content.

When possible, use checks that are specific to the task. Compare the accuracy gain with the cost of the added tokens and latency.

<h2 id="retrieval-and-tools">Retrieval and tools</h2>

Retrieval-augmented generation (RAG) does these steps:

1. Search an external collection.
2. Rank the candidate passages.
3. Put the selected evidence into the context.
4. Ask the model to answer from this evidence.

Failures can occur in indexing, query construction, ranking, context assembly or generation. Citations help users examine the grounding. But a citation alone does not prove that the claim comes from the cited passage.

Tool use extends the workflow. The model selects a function and writes the arguments. Then it gets a result and continues. Calculators, databases, search systems and business APIs give exact or current results. The model must not try to copy these results from its memory.

> **Caution:** Retrieval text and tool output are data at a security boundary. They can give information for the answer. But they must not secretly change what the application can do.

Applications must do these tasks:

- Validate the tool names and the arguments.
- Limit the permissions.
- Stop failed operations after a time limit.
- Keep untrusted results separate from system instructions.
