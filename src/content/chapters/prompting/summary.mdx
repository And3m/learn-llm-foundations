Prompting changes the behavior of a model through its input. A prompt can do these things without an update to the base model:

- Define the task.
- Show a mapping.
- Give evidence.
- Give more compute at inference time.
- Give access to tools.

<h2 id="mental-model">The chapter in one mental model</h2>

$$
\text{instruction} + \text{context} + \text{examples} + \text{tools}
\longrightarrow P(\text{response} \mid \text{prompt})
$$

All the parts of the prompt together set the probability of each possible response.

Each part that you add must remove a real uncertainty. It must answer one of these questions:

- What must the model do?
- Which facts must it use?
- What does a valid answer look like?
- Where can the model get missing information?

<h2 id="method-guide">Method guide</h2>

| Need | Start with |
| --- | --- |
| A clear task and format | A direct instruction and an output contract |
| A difficult label or mapping | Typical few-shot examples |
| A problem with many steps | Explicit decomposition |
| Better candidate quality | Refinement or diverse sampling |
| Current or private facts | Retrieval with grounded citations |
| An exact calculation or action | A validated tool with limited permissions |
| Task specialization with few parameters | Soft prompts or a different parameter-efficient method |

Select the lightest method that satisfies the requirement. Each extra call, sample and context token adds latency and cost.

<h2 id="evaluation-guide">Evaluation guide</h2>

Evaluate prompts on typical held-out cases. Include these cases:

- Missing evidence.
- Ambiguous instructions.
- Long inputs.
- Hostile text.
- Format failures.

Measure the task quality together with token use, latency, parse validity, citation support and tool safety. Run the tests again when the model, the retrieval index or the prompt template changes.

Prompting guides the model. It does not give guarantees. When the application can enforce a rule directly, keep the validation and the permission checks outside the model.
