This lesson is about decoder-only large language models (LLMs). Most modern LLMs use this design, but some use an encoder-decoder design. Their data, parameters and compute are large enough to transfer to many tasks. Pre-training alone does not make its visible behavior. Task fine-tuning, alignment, prompting and decoding all change the same probability model.

<h2 id="decoder-only-transformers">Decoder-only Transformers</h2>

For the tokens $x_0,\ldots,x_m$, a causal language model factorizes the probability of the sequence:

$$
\Pr_\theta(x_0,\ldots,x_m)
=
\prod_{i=0}^{m}\Pr_\theta(x_i\mid x_{<i})
$$

The probability of the full sequence is the product of the probabilities of each token, given the tokens before it.

A decoder block has two parts: masked multi-head self-attention and a feed-forward network. The causal mask stops position $i$ from reading the tokens after it. Residual connections and layer normalization keep the deep stack stable. Modern models often use pre-normalization, so that the residual path stays direct.

The model projects the final hidden state at each position over the vocabulary. Cross-entropy increases the probability of the observed next token. During generation, the model does these steps again and again:

1. Calculate the distribution for the next position.
2. Select a token.
3. Add the token to the sequence.

| Vocabulary projection | Gives the next-token logits |

These settings control the model size: depth, width, feed-forward size, vocabulary and the configuration of the attention heads. The parameter count describes capacity, not training quality. A large model with too little training can be less useful than a smaller model. The smaller model can have a better balance between compute and data.

<h2 id="training-llms">Training LLMs</h2>

Pre-training minimizes the negative log likelihood over a corpus $D$:

$$
\hat{\theta}
=
\arg\min_\theta
\sum_{x\in D}\sum_i
-\log\Pr_\theta(x_i\mid x_{<i})
$$

Training finds the parameters that give the highest probability to each next token in the corpus.

Each document gives many prediction events. The objective is simple. But the learned representation depends on many choices:

- Tokenization.
- The mix of data in the corpus.
- Sequence length.
- The optimizer and the training schedule.
- Numerical precision.
- Model architecture.

Training uses minibatches. Backpropagation adds up gradients through the full layer stack, and an optimizer updates billions of parameters. Monitor the checkpoints, the validation loss, the gradient norms and the hardware health. A failure late in a long run is expensive.

<h2 id="fine-tuning-llms">Fine-tuning LLMs</h2>

Pre-training teaches a model to continue text from the training distribution. Fine-tuning changes the distribution that the model must copy.

### Supervised task tuning

For an input $x$ and a desired response $y$, conditional fine-tuning minimizes this loss:

$$
\mathcal{L}_{\mathrm{SFT}}
=
-\sum_t\log\Pr_\theta(y_t\mid x,y_{<t})
$$

The loss increases the probability of each response token, given the input and the response tokens before it.

Usually, the loss applies to the response tokens and not to the user instruction. Task datasets can teach these skills:

- Classification as label generation.
- Structured extraction.
- Summarization.
- Dialogue.
- Writing for a specific domain.

### Parameter update choices

- **Full fine-tuning** updates the full model. It gives the most flexibility.
- **Parameter-efficient tuning** updates adapters or low-rank parameter changes. The base weights do not change.
- **Continued pre-training** uses more unlabeled domain text before the instruction examples.

These stages solve different problems. Continued pre-training changes the knowledge and the language statistics. Supervised tuning teaches an input-output policy. A domain model can need the two stages.

Fine-tuning data is much smaller and more specific than pre-training data. Thus, data errors and repeated response styles have a larger effect. Good validation must measure three things:

- Task quality.
- Behavior outside the tuned domain.
- Signs of forgetting.

<h2 id="aligning-llms">Aligning LLMs</h2>

Maximum likelihood rewards text that looks like the training text. It does not always reward helpful, true or harmless answers, or answers that follow instructions. Alignment adds human behavior signals after a capable initial model exists.

This is a usual pipeline:

1. **Supervised fine-tuning:** Copy selected instruction-response demonstrations.
2. **Preference collection:** Compare candidate responses for the same prompt.
3. **Preference optimization:** Train a reward model and use reinforcement learning. Or use a direct objective, for example DPO.

Alignment moves the policy toward the preferred responses. A reference limit stops the policy from moving too far from the original language model. The target is still empirical. Preferences depend on the annotator guidance, cultural assumptions, the task context and the quality of the candidate responses.

<Callout title="Architecture is not behavior">
  <p>Two systems can have the same decoder architecture and the same parameter count, but behave differently. Their corpora, instruction data, preference data, system prompts and decoding rules can be different.</p>
</Callout>

<h2 id="prompting-llms">Prompting LLMs</h2>

Prompting changes the conditional context. It does not update the parameters. The prompt can contain these parts:

- An instruction that defines the action.
- Evidence or background facts.
- Demonstrations of the desired mapping.
- Conversation history.
- An output schema or a stop condition.

Zero-shot prompts give only instructions. Few-shot prompts add demonstrations. This allows **in-context learning**: the model finds a temporary task pattern from its input. Reasoning prompts can ask for intermediate calculation. Retrieval and tool calls can give information or operations that the model does not store reliably.

Then, generation depends on a decoding policy:

- Greedy decoding selects the token with the largest probability.
- Sampling adds controlled diversity.
- Search or verification can compare more than one candidate.

Thus, the assistant is a system:

$$
\text{model}
+
\text{prompt}
+
\text{external context}
+
\text{decoder}
+
\text{policy controls}
$$

The assistant output comes from five parts together, not from the model alone.

Each part can change the observed answer. When you debug an LLM application, find which part gave the wrong assumption. Do not always say that "the model" caused the failure.
