Training at scale must balance four resources that are connected: data, parameters, arithmetic and communication. If you increase one resource and do not increase the others, you get an expensive bottleneck, not a better model.

<h2 id="data-preparation">Data preparation</h2>

There is much raw web text. But raw text is not always good for training. A practical pipeline usually does these steps:

1. **Extraction and normalization:** Recover readable text and use consistent encodings.
2. **Language and quality filtering:** Remove documents that are damaged or that contain little information.
3. **Deduplication:** Remove exact duplicates and near-duplicates.
4. **Safety, privacy and policy filtering:** Remove content that must not go into training.
5. **Mixture weighting:** Set the quantity of each source, for example domains, languages, code, books, papers and conversations.
6. **Tokenization and packing:** Put the tokens into training sequences with as little padding as possible.

Deduplication is necessary for three reasons:

- Repeated documents change the effective distribution.
- They use compute for no benefit.
- They increase the risk of memorization.

Strong filtering can remove most of the scraped data. But the filter itself adds preferences about language, style and quality.

The corpus mix has the same effect as a model parameter. If you give more weight to code, mathematics or a language with little data, the skills and trade-offs of the model change. This occurs even when the architecture and the token budget stay the same.

<h2 id="model-modifications">Model changes</h2>

Large decoder architectures keep the Transformer core. But they change some components for stability and efficiency:

- **Pre-normalization** applies layer normalization before attention or the feed-forward network. This makes the gradient flow better through deep residual stacks.
- **RMS-style normalization** normalizes the magnitude. It uses less compute than full mean-and-variance normalization.
- **Gated feed-forward networks** combine an activation gate with a value projection. They often use parameters better.
- **Rotary or relative positions** encode the distance between tokens in attention. They also help later context extension.
- **Grouped-query or multi-query attention** decreases the number of key and value heads. This decreases the memory of the inference cache.

This is a standard feed-forward layer:

$$
\operatorname{FFN}(h)
=
\sigma(hW_1+b_1)W_2+b_2
$$

The layer projects $h$ to a larger hidden size, applies the activation $\sigma$, and then projects back.

The hidden dimension is usually some times larger than the model width. Thus, this sublayer contains a large part of the parameters and the compute. Gating can make the layer more expressive. But larger hidden dimensions increase the training cost and the serving cost.

Evaluate architecture changes as a system. A change that makes training more stable can have an effect on kernel efficiency. An attention design that saves cache memory changes the cost of inference, even if the pre-training cost is almost the same.

<h2 id="distributed-training">Distributed training</h2>

One accelerator cannot hold the largest model, its optimizer state, its activations and the batch. Distributed training divides these items along some axes.

| Strategy | What it divides | Main communication |
| --- | --- | --- |
| Data parallelism | Minibatch examples | Gradient synchronization |
| Tensor parallelism | Matrix operations inside layers | Partial activations or results |
| Pipeline parallelism | Groups of layers in sequence | Activations between stages |
| State sharding | Parameters, gradients and optimizer state | Gather or reduce when necessary |

<ParallelismDiagram />

In data parallelism, worker $k$ calculates a gradient on its data shard $D_k$. Then the workers combine their gradients:

$$
g
=
\frac{1}{N}\sum_{k=1}^{N}
\nabla_\theta\mathcal{L}_\theta(D_k)
$$

The final gradient $g$ is the average of the gradients from all $N$ workers.

Each strategy solves a different problem:

- Tensor parallelism puts wide layers across devices.
- Pipeline parallelism puts deep stacks across devices. But it makes "bubbles" when stages wait.
- State sharding decreases memory that is repeated on each device.

Large systems use all three. Thus, the network topology and the collective communication are as important as the number of devices.

Low-precision training decreases memory traffic and makes matrix multiplication faster. Master weights, loss scaling or carefully selected formats keep enough dynamic range for stable updates. Activation checkpointing does more calculation again, but it uses less memory.

The useful metric is not the peak hardware throughput. It is the continuous training progress for each unit of time and cost. These items all decrease utilization: data loading, synchronization, slow workers, failures and checkpoint writes.

<h2 id="scaling-laws">Scaling laws</h2>

Empirical scaling laws give an approximate validation loss as a power law. The law uses one of three resources:

- The model parameters $N$.
- The dataset size $D$.
- The compute $C$.

$$
\mathcal{L}(N)\approx aN^{-\alpha}+b,
\qquad
\mathcal{L}(D)\approx cD^{-\beta}+d
$$

The loss decreases as a power of $N$ or $D$, and it moves toward a floor ($b$ or $d$) that it cannot go below.

Power laws are useful because small runs can forecast larger runs inside the observed range. They also show bottlenecks:

- More parameters give a smaller benefit each time if the model sees too few tokens.
- Very large data with too little capacity stops giving benefit after some time.

**Compute-optimal training** selects $N$ and $D$ together for a fixed compute budget. Deployment can change the best choice. If the model serves billions of requests, a smaller model with more training tokens can be better. Its training costs more, but its serving costs much less.

Scaling laws also have limits:

- The coefficients depend on the architecture, the data, the tokenizer and the metric.
- Trends on downstream tasks can be different from the pre-training loss.
- A smooth average does not predict one specific new skill.
- Distribution shifts and data quality can make the extrapolation wrong.

Use scaling laws to plan experiments and budgets. Then validate the model on the real set of skills and risks.
