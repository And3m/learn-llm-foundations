Inference is the process that uses a trained model and a request to make generated tokens. Inference has two phases. Each phase uses compute in a different way. The decoding rule changes the quality, the diversity and the cost of the result.

<h2 id="inference-preliminaries">Inference preliminaries</h2>

A request goes through these steps:

1. The serving stack splits the prompt into tokens.
2. It builds the positions and the masks.
3. It puts the request into a scheduler.
4. The model calculates the logits for the next token.
5. A decoding policy changes the logits into a token choice.
6. The system adds this token to the sequence.
7. Steps 4 to 6 occur again until a stop condition or the token limit.

For the vocabulary logits $z$, this is the next-token distribution:

$$
P(y_t=i \mid x,y_{<t}) = \frac{\exp(z_i)}{\sum_j \exp(z_j)}.
$$

The softmax changes each logit $z_i$ into the probability that the next token is token $i$.

Generation is sequential at the token boundary. Token $t+1$ depends on the token that the model selected at step $t$. Systems get efficiency back in two ways:

- They do the work inside each step in parallel.
- They process many requests together.

<h2 id="two-phase-inference">The two-phase framework</h2>

**Prefilling** sends all the prompt tokens through the Transformer. Large matrix operations run across the positions in parallel. This phase makes the attention keys and values for each layer. It ends with the distribution for the first output token.

**Decoding** processes one new selected token for each request at each step. It also reads the cached keys and values for the full context. The operations are smaller, and the scheduler runs them again and again. Thus, the main bottlenecks are memory bandwidth, cache capacity and request coordination.

Long prompts increase the prefill time. Long responses increase the number of sequential decode steps. Keep these two dimensions separate when you find the cause of latency, or when you decide which optimization to use.

<h2 id="decoding-algorithms">Decoding algorithms</h2>

**Greedy decoding** selects the token with the highest probability at each step. It always gives the same result, and it costs little. But it can select a continuation that looks good locally too early.

**Beam search** keeps some partial sequences and expands the sequences with the best total scores. It is useful for sequence tasks with limits. But it uses more memory and compute.

**Sampling** keeps diversity, because it takes a random draw from the next-token distribution. Temperature changes the scale of the logits:

$$
P_T(i) \propto \exp(z_i/T),
$$

Each logit is divided by the temperature $T$ before the softmax.

- A lower $T$ puts more probability on the top tokens.
- A higher $T$ makes the distribution flatter.
- **Top-$k$ sampling** limits the choice to the $k$ most probable tokens.
- **Nucleus (top-$p$) sampling** keeps the smallest set of tokens whose total probability gets to $p$.

<SamplingDiagram />

No decoder is the best for all tasks:

- Exact tasks, or tasks that need low variance, need careful choices and validation.
- Creative tasks need diversity.
- For problems with a reliable verifier, sample some candidates and select from them.

<h2 id="serving-metrics">Serving metrics</h2>

Tokens per second is not sufficient to measure system quality. Use these metrics:

| Metric | What it measures | How the user usually feels it |
| --- | --- | --- |
| Time to first token (TTFT) | From arrival to the first generated token | First response speed |
| Inter-token latency (ITL) | Time between streamed tokens | Smoothness of the output |
| End-to-end latency | From arrival to the full response | Total wait |
| Throughput | Tokens or requests completed in a unit of time | Efficiency of the fleet |
| Goodput | Work that meets a service target | Useful capacity |
| Memory and utilization | How much of the resources is in use and active | Margin for cost |

Interactive chat can give priority to TTFT and steady streaming. Offline evaluation can accept a queue delay to get the maximum throughput. Report distributions and tail latency, not only averages. A small group of long requests can control the user experience.
