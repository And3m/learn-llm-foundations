Efficient serving does three things:

- It does not repeat calculations.
- It keeps the accelerators busy with useful work.
- It distributes the model or the traffic when one device is not sufficient.

The best design follows the workload. It does not follow one benchmark number.

<h2 id="more-caching">Prefix and KV caching</h2>

Token-by-token attention uses all the earlier keys and values again. A key-value (KV) cache stores these tensors for each layer. Thus, each decode step calculates only the state of the newest token. Without the cache, the model must calculate the full prefix again after each generated token.

<KvCacheDiagram />

The cache uses memory to save arithmetic. Its size increases with these values:

- The sequence length.
- The number of layers.
- The precision.
- The batch size.
- The number of KV heads.

Multi-query attention and grouped-query attention decrease the memory, because query heads share keys and values. Paged or blocked allocation decreases fragmentation when requests have different lengths.

Prefix caching uses the same KV state for requests that start with the same system prompt or document prefix. This needs exactly the same tokens. You must also clear the cache carefully when the model, the adapters or the prompt changes. Eviction and admission policies decide where the cache memory goes: to prefixes that many requests use, or to active generations.

<h2 id="batching">Batching</h2>

Batching combines requests, so that the matrix multiplications are large enough to use the accelerator capacity. A static batch starts and ends together. Thus, it wastes slots when the sequences have different lengths. Padding also uses compute on positions that do not contain useful tokens.

**Continuous batching** (also called iteration-level batching) updates the batch between decode steps:

- Completed requests leave the batch.
- Waiting requests go into the batch.

This increases utilization for online traffic. But the scheduler must balance the prefill work, the decode latency, the queue and the available KV memory.

Larger batches usually increase throughput. But they also increase the queue delay and the cache pressure. Chunked prefilling can divide a very long prompt into parts, so that it does not block many short decode steps. Service tiers, deadlines and estimates of the prompt and output lengths can help set the priority. Large requests must still get service.

<h2 id="parallelism">Parallelism</h2>

When a model does not fit on one device, or one device cannot meet the demand, inference uses parallelism:

- **Tensor parallelism** divides the operations inside a layer.
- **Pipeline parallelism** puts groups of layers on different devices.
- **Data parallelism** puts a copy of the model on each device to serve independent traffic.

Each one adds communication, synchronization or time when stages wait.

Speculative decoding decreases sequential latency in a different way:

1. A smaller draft model proposes some tokens.
2. The target model checks them in one parallel pass.
3. The accepted tokens move generation forward by more than one position.

With the correct acceptance rule, the output keeps the distribution of the target model. The speedup depends on how accurate the draft is, and on the cost of drafting compared with verification.

<h2 id="serving-remarks">Practical remarks</h2>

Quantization, optimized kernels, model architecture, cache policy, batching and parallel placement all have effects on each other. A method that helps one phase can make a different phase worse:

- A larger batch increases throughput, but it can break the TTFT target.
- Strong quantization saves bandwidth, but it can decrease task quality.

Profile the real prompt lengths, output lengths, arrival patterns, hardware topology and latency targets. Compare quality at the same serving cost. When raw throughput hides late responses, use goodput against a service-level objective.
