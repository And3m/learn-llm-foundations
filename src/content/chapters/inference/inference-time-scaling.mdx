Model quality can become better when you use more compute after training. Inference-time scaling gives a request more evidence, more candidates or more reasoning paths. It puts the larger budget where it is useful.

<h2 id="context-scaling">Context scaling</h2>

One method gives the model more related information:

- Retrieve more passages.
- Examine near documents.
- Query again and again for missing evidence.

Longer context is useful only when it contains a signal that the model can use. Unrelated or conflicting text can distract the model. It also increases the prefill cost and uses KV memory.

Retrieval ranking, deduplication, compression and citation requirements help keep the evidence dense. Context scaling works best when the answer depends on external knowledge that you can find and check. It helps less when the problem is a new deduction and not missing facts.

<h2 id="search-scaling">Search scaling</h2>

Search generates many partial or complete solutions. It uses a score to decide which paths to extend.

- **Best-of-$N$ sampling** selects the candidate with the highest score.
- **Tree-based methods** branch at intermediate steps and keep the good states. When a path fails, they go back.

The compute budget can be fixed. Or it can increase for requests that are not certain or that have high value.

Search helps only when two conditions are true:

- The candidates are diverse enough to give a chance of improvement.
- The score agrees with the real quality.

If these conditions are not true, more branches repeat the same error or optimize a weak judge. Monitor the added gain as the budget increases, because the returns usually decrease.

<h2 id="output-ensembling">Output ensembling</h2>

Ensembling combines independent outputs. It does not select only one highest score.

- A majority vote works for discrete answers.
- Weighted voting, ranking or a judge can combine longer responses.
- Self-consistency samples many reasoning paths and selects the conclusion that most paths agree on.

Agreement is evidence only when the errors are not fully correlated. Models with the same training, or with the same prompt, can have the same blind spot. Thus, add useful diversity. Normalize the answers before the vote. When possible, prefer validation that you can run or that uses sources.

<h2 id="thinking-paths">Generate and verify paths</h2>

For mathematics, code, planning and other structured tasks, a system can generate intermediate steps and verify them one by one:

- Process reward models give scores to partial paths.
- External checkers run code or validate limits.
- Critique-and-revision loops repair a draft.

A verifier can stop an invalid branch before the system uses the full generation budget.

Adaptive policies keep extra compute for difficult requests. Easy inputs finish after one pass. Inputs that are not certain start more context, more samples, more search or a stronger model. Thus, serving becomes a decision about how to use compute, not only a choice of token sampler.

<Callout title="The verifier gives the benefit">
  <p>More candidates are useful only when the system can find the better ones. Prefer tests, grounded evidence or independently trained evaluators to confidence alone.</p>
</Callout>
